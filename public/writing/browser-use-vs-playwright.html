browser-use⚔️Playwright

AI 原生浏览器自动化 vs 老牌自动化框架 —— 一对"师徒"的地盘争夺战

⚡ 核心结论(先看这个)

两者不在同一层级,但正在互相入侵。Playwright 是确定性的自动化基础设施——你写精确脚本,它分毫不差地执行;browser-use 是概率性的 AI Agent——你用自然语言描述意图,LLM 自己琢磨怎么点。

有趣的恩怨:browser-use 诞生时就构建在 Playwright 生态之上(GitHub topics 至今挂着 playwright 标签),而微软如今推出 Playwright MCP / CLI,反手杀进了 AI Agent 浏览器控制这个对方的主场。

一句话:写测试选 Playwright 没有悬念;让 AI 自主闯荡开放网页选 browser-use;最佳实践往往是混用。

🎯 本质差异:确定性 vs 概率性

Playwright —— 你说一步,它走一步

哲学:开发者用代码精确描述每一步操作,框架保证分毫不差、万次执行结果一致。

  • 自动等待 + Web-First 断言,消灭 flaky test
  • 语义化定位器(getByRole/getByLabel),不靠脆弱选择器
  • 追踪回放、截图、录屏,测试失败可查案发现场
  • 并行执行、认证状态复用,为 CI 而生

一句话:浏览器自动化的"数控机床"。

browser-use —— 你说目标,它自己想辙

哲学:用户用自然语言描述任务目标,LLM Agent 自主规划、观察页面、决策操作、处理意外。

  • "用我的简历填这份求职申请" → Agent 自己搞定
  • 自研 bu-* 模型,比通用 LLM 快 3-5 倍
  • Odysseys 排行榜第一(87.4%,200 个长时程任务)
  • 云服务提供隐身指纹/代理轮换/CAPTCHA 处理

一句话:浏览器自动化的"自动驾驶"。

🤖 AI 能力路线之争(本场最有意思的部分)

两家都在抢"AI Agent 控制浏览器"这块蛋糕,但技术路线截然不同:

维度browser-usePlaywright MCP / CLI
决策方式LLM 持续在环:观察→思考→行动循环Agent 调用确定性工具,LLM 只做编排
页面表示DOM 序列化 + 可选截图,喂给 LLM结构化无障碍快照 + 元素引用(e5、e10),无需视觉模型
Token 消耗高:每步都要把页面状态喂给 LLM低:CLI 模式刻意省 token(不加载大量 schema)
失败模式可能"瞎编"操作路径,概率性失误工具调用失败就是明确报错,可调试
模型依赖必须接 LLM(自研 bu-* / GPT / Claude / Gemini / Ollama)无强依赖,任何 Agent 都能挂
适用任务开放式、长尾、没见过的网站结构化、可枚举、需要审计的操作

点评:browser-use 赌的是"模型足够聪明,规划交给 AI";Playwright 赌的是"确定性才是生产力,LLM 只配当调度员"。2026 年的现实是——两种哲学都活得很好,因为干的活本来就不一样。

💰 成本账(很多人忽略的一节)

Playwright:零边际成本

  • 开源免费,Apache-2.0
  • 执行自动化不烧任何 LLM token
  • CI 里跑一万次,成本就是电费
  • 挂 MCP 给 Agent 用时才有模型调用,且 CLI 模式刻意压 token

browser-use:按任务付费

  • 库本身 MIT 免费,但每次任务都在烧 LLM token
  • 自研 bu-* 模型快 3-5 倍,也是在压这笔账
  • 云服务(隐身/代理/CAPTCHA/1000+ 集成)是付费订阅
  • 典型 open-core:开源引流,云端变现

⚠️ 风险雷达

browser-use 版本号 0.13.7:一个 10.7 万 star 的项目还在 0.x 游荡,意味着 API 随时可能翻脸。跟它升级要盯 changelog,生产环境务必锁版本。
browser-use 的 LLM 成本不可小觑:开放式任务每一步都在调用模型。跑通一次 demo 很爽,规模化跑一万次时账单会很感人。预算敏感的场景先算清 token 账。
Chromium only:browser-use 只支持 Chromium。需要 WebKit(Safari 内核)或多浏览器兼容性验证的场景,它直接出局。
Playwright 做 AI 是"顺手":MCP/CLI 是主航道(E2E 测试)之外的延伸。它的 AI 能力永远服务于"让 Agent 用确定性工具",不会去做 browser-use 那种全自主规划——这既是边界也是天花板。
商业依赖:browser-use 的看家本领(隐身、代理、CAPTCHA、1000+ 集成)拴在自家云服务上;Playwright 背靠微软,倒闭风险约等于零,但功能是社区投票说了算。
值得肯定:browser-use 把 benchmark 完全开源(browser-use/benchmark),Odysseys 87.4% 是第三方榜单成绩,不是自娱自乐;Playwright 的 issue hygiene(156 个 open)对一个 9.3 万 star 的项目堪称模范。

🧭 选型决策树

「我要写 E2E 测试 / 接 CI 流水线」

→ Playwright,没有悬念。测试运行器、追踪、并行、多浏览器,这本来就是它的主场。

「重复、精确、高频的自动化(定时抓数、RPA)」

→ Playwright。确定性 + 零 LLM 成本,跑一百万次也一样稳。

「让 AI Agent 自主完成开放式网页任务(没见过的网站、长尾操作)」

→ browser-use。你没法为全网每个网站都写脚本,这正是 LLM 在环的价值。

「给 Claude Code / Cursor 这类 coding agent 加浏览器能力」

→ 都行,看口味:Playwright CLI/MCP 更省 token 更可预测;browser-use skill 更自主更能处理意外页面。

「最佳实践?」

→ 混合双打:用 browser-use 探索、验证可行性(AI 趟路),跑通后把稳定流程固化成 Playwright 脚本进生产(确定性接管)。探索期买灵活,量产期买可靠。
